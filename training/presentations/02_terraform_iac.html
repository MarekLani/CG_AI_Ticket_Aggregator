HCL syntax

Terraform konfigurácia je čitateľná, ale stále presná

Bloky

Blok hovorí, aký typ veci definujeme: `terraform`, `provider`, `resource`, `variable`, `output` alebo `module`.

Argumenty a výrazy

Argument nastavuje vlastnosť. Výraz môže používať premenné, funkcie, podmienky alebo referencie na iné resources.

resource "azurerm_resource_group" "main" { name = "rg-${var.project}-${var.environment}" location = var.location tags = { environment = var.environment owner = "platform" } }

Provider

Provider je most medzi Terraformom a konkrétnou platformou

terraform { required_providers { azurerm = { source = "hashicorp/azurerm" version = "~> 4.0" } } } provider "azurerm" { features {} }

Provider verzujeme rovnako zámerne ako aplikačné závislosti. Náhodný upgrade providera môže zmeniť správanie plánov.

Resources a referencie

Resources sa navzájom prepájajú cez referencie

resource "azurerm_storage_account" "state" { name = var.storage_account_name resource_group_name = azurerm_resource_group.main.name location = azurerm_resource_group.main.location account_tier = "Standard" account_replication_type = "LRS" }

Keď resource odkazuje na iný resource, Terraform z toho vie odvodiť závislosť. V mnohých prípadoch preto netreba písať `depends_on` ručne.

Premenné

Premenné robia konfiguráciu použiteľnú pre viac prostredí

variable "environment" { type = string description = "Deployment environment name." validation { condition = contains(["dev", "prod"], var.environment) error_message = "Environment must be dev or prod." } } variable "location" { type = string default = "westeurope" }

V kóde potom používame `var.environment` alebo `var.location`. Hodnoty sa dajú dodať cez `.tfvars`, CLI alebo premenné prostredia.

tfvars

Parametre prostredia nepatria natvrdo do resource blokov

dev.tfvars

prod.tfvars

Locals, data, outputs

Nie všetko je resource

locals

Pomenujú odvodené hodnoty, napríklad spoločný prefix názvov.

locals { name_prefix = "uwi-${var.environment}" }

data

Načíta existujúci objekt, ktorý Terraform nemusí vlastniť.

data "azurerm_client_config" "current" {}

outputs

Zverejnia hodnotu pre človeka, pipeline alebo nadväzujúci modul.

output "api_url" { value = azurerm_linux_function_app.api.default_hostname }

State

State je citlivá prevádzková evidencia

Mapovanie

Spája Terraform resource s reálnym Azure resource.

Spolupráca

Pre tím patrí do remote backendu so zamykaním, nie do lokálneho súboru v repozitári.

Bezpečnosť

Môže obsahovať citlivé hodnoty, preto potrebuje riadený prístup.

State neupravujeme ručne ako bežný JSON súbor. Zmeny v state sa robia iba vedome cez Terraform nástroje.

Bežný workflow

Najprv čítame plán, až potom meníme infraštruktúru

terraform init # pripraví working directory a providery terraform fmt # zjednotí formát terraform validate # skontroluje konfiguráciu terraform plan # ukáže navrhované zmeny terraform apply # vykoná odsúhlasenú zmenu

V tímovej práci je `plan` review artifact. Nemá len „prejsť“, ale má dávať zmysel.

Terraform / IaCTechnologická vsuvka · Unified Work Items
Ako čítať plan

Symboly v pláne sú dôležitejšie než dlhý výpis

+ create

Vznikne nový resource.

~ update

Existujúci resource sa zmení na mieste.

- destroy

Resource sa odstráni. Toto vždy čítať veľmi pozorne.

Pri infra review sa nepýtame len „prešla validácia?“, ale aj „sú tieto zmeny očakávané a bezpečné?“

Moduly

Modul je rozhranie pre opakovateľný infra pattern

Príliš skoro

Modul bez reálneho opakovania môže skryť jednoduchú infraštruktúru za zbytočnú abstrakciu.

V správny čas

Modul dáva zmysel, keď opakujeme rovnaký pattern alebo chceme vedome stabilizovať rozhranie.

module "app_insights" { source = "./modules/application-insights" name_prefix = local.name_prefix location = var.location }

Repo boundary

V našom projekte je infraštruktúra samostatný repozitár

Aplikačný repozitár

Kód aplikácie, aplikačná architektúra, štandardy, runtime požiadavky a budúce DB migrácie.

Infraštruktúrny repozitár

Terraform, Azure resources, networking, platformová identita/RBAC, konfigurácia prostredí a nasadenie infraštruktúry.

Toto je zámerné architektonické rozdelenie. Aplikačný repozitár hovorí, čo potrebuje; infra repozitár rozhoduje, ako to presne nasadiť.

Terraform vs. Bicep

Bicep je výborný pre Azure. Terraform vyhráva ako širší infra workflow.

Bicep

  • veľmi dobrá Azure-native skúsenosť;
  • bez samostatného state súboru;
  • rýchla podpora nových Azure resource typov;
  • jednoduchší jazyk pre tímy zamerané len na Azure.

Terraform

  • rovnaký workflow pre viac providerov;
  • silný ekosystém modulov a providerov;
  • jasný plan/apply model;
  • dobrá zhoda s GitHub review a pipeline procesom.

Pre tento projekt je dôležité mať konzistentný infra workflow v samostatnom repozitári. Preto pracujeme s Terraformom, aj keď Bicep ostáva relevantná Azure alternatíva.

Bezpečnosť

Terraform nemá byť nosičom hesiel

  • Preferovať workload identity / OIDC medzi GitHub Actions a Azure.
  • Hodnoty špecifické pre prostredie držať v riadených pipeline/environment mechanizmoch.
  • Secret nikdy nemá skončiť v commite, PR komentári, logu ani Terraform outpute bez veľmi dobrého dôvodu.
  • State backend musí mať obmedzený prístup a zamykanie proti súbežným zmenám.
