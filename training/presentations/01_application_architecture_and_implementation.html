Hranice riešenia

Zodpovednosti jednotlivých vrstiev

Konektory

Komunikujú s konkrétnym zdrojom a mapujú jeho údaje.

Aplikačná vrstva

Obsahuje jednotný model nezávislý od zdroja a aplikačnú logiku.

API

Poskytuje stabilné HTTP rozhranie pre frontend.

Frontend

Zobrazuje pracovné položky, filtre a používateľské stavy.

Dôležitá hranica: Azure infraštruktúra a jej Terraform definícia sa riešia v samostatnom infra repozitári. Tento repozitár definuje iba požiadavky aplikácie na infraštruktúru.
Modulárny návrh
Backend

.NET 10 a Azure Functions pre backend aplikácie

.NET 10

Silné typovanie, DI, asynchrónne I/O a dobré oddelenie integračných rozhraní.

Azure Functions (isolated)

Dnes obsluhujú HTTP API; neskôr môžu slúžiť aj na časované spracovanie alebo spracovanie na pozadí bez zmeny aplikačného modelu.

Triggery bez biznis logiky

Trigger iba prijme vstup a odovzdá ho aplikačnej logike. Biznis pravidlá zostávajú mimo triggerov.

Aplikačný model zostáva nezávislý od hostingu v Azure Functions.

Technologická voľba
Frontend

Frontend: React, TypeScript a vybrané knižnice

React + TypeScript + Vite

Základ SPA, striktné typovanie a rýchly vývoj aj build.

Aplikačné stránky a komponenty bez ďalšej frameworkovej vrstvy.

Material UI + Data Grid

Hotové UI komponenty a tabuľka vhodná pre zoznam pracovných položiek.

Použijeme hotové komponenty namiesto vlastnej knižnice a gridu.

TanStack Query

Rieši načítanie dát z API, cache, stavy načítavania a chýb aj invalidáciu.

Serverový stav nemusíme riešiť vlastným globálnym storom.

React Router

Navigácia a stav v URL tam, kde má byť možné zdieľať konkrétny pohľad alebo filter.

Frontend komunikuje iba s naším HTTP API.
Technologická voľba
Platformové rozhodnutia

Autentifikácia, observabilita, testovanie a databáza

Entra ID

Prihlásenie používateľa, tokeny pre API a spravovaná identita pre služby v Azure.

Application Insights

Telemetria frontendu a backendu je oddelená, ale dá sa navzájom korelovať.

Automatické testy

xUnit pre backend, Vitest/RTL pre frontend a Playwright pre vybrané E2E scenáre.

PostgreSQL neskôr

Databázu pridáme až vtedy, keď vznikne konkrétna potreba cachovania, synchronizácie, histórie alebo stavu spravovaného aplikáciou.

Databáza podľa potreby

Databázu pridáme iba vtedy, keď rieši konkrétnu potrebu

Prvá verzia

Helpdesk → konektor → WorkItem → API → React. Bez aplikačnej databázy.

Neskôr podľa potreby

PostgreSQL + EF Core až pri cachovaní, pravidelnej synchronizácii, histórii, agregáciách alebo stave spravovanom aplikáciou.

Aj po pridaní databázy zostávajú Helpdesk, Planner a GitHub primárnym miestom správy údajov. Databáza aplikácie nenahrádza zdrojové systémy.
